# 1.5.4 verification

The status hang was reproduced in the installed 1.5.3 app. Child pluginkit processes were blocked in `__write_nocancel` while both app actors called `waitUntilExit()` before reading stdout. The same source pattern exists in tag v1.5.0; it was not introduced by the GPX/GAP diff, but release QA missed it.

An isolated copy of that old runner deadlocked with 256 KiB output. The replacement completed large stdout/stderr, parallel commands and real pluginkit queries. It terminates a hung owned child after five seconds and returns failure rather than treating an installed bundle or failed scan as proof of success.

Validation:

- 219 XCTest tests, 0 failures (`/tmp/dotviewer-status-final-tests.log`).
- 13 Python tests pass, including DropDMG failure and stale-artifact rejection.
- Explicit reuse with build 999 rejected the 1.5.4 (11) export before notarization/packaging.
- Universal Release app built with unmodified Apple clang/clang++, using documented compiler-forwarding wrappers to avoid the separate Xcode compiler-discovery hang. A test C object built directly and through the wrapper was byte-identical.
- Xcode's export codesign child was also sampled blocked in a pipe write. Explicit signing preserves entitlements except development debugging permission, removes development profiles, verifies all nested bundles and checks Developer ID/team identity. See `scripts/sign-developer-id-app.py` and `WORKFLOW.md`.
- Native Status GUI reached `Extension Enabled`, `dotViewer is ready`, and completed conflicts. Both refresh buttons completed repeatedly. Initial post-install delayed system responses produced the new retryable error instead of endless loading; retry recovered to green.
- DropDMG `dotviewer` profile produced the saved purple background, dotted arrow, left-hand app and right-hand Applications alias. Compared visually with the user's 1.5.0 screenshot. No plain-DMG fallback is allowed.

The original notarized 1.5.3 app is preserved at `/tmp/dotviewer-status-original-1.5.3.review-bundle`. Public release completion and hashes are recorded separately in the work log when verified.
